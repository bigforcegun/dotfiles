## Пороги считаются из экономики, а не подбираются

Если вероятность откалибрована, оптимальный порог бинарного решения — арифметика:

```
t = C_FP / (C_FP + C_FN)
```

`C_FP` — цена ложного срабатывания, `C_FN` — цена пропуска.

- Эскалация тикета: зря дёрнули дежурного vs проспали падение выплат, 1:50 → **t ≈ 0.02**.
- Автозакрытие как спам: закрыли живого клиента vs прочитали спам, 20:1 → **t ≈ 0.95**.

Вся ценность калибровки здесь: порог перестаёт быть магическим числом и становится
следствием бизнес-цены. Вопрос «во сколько раз пропуск хуже ложной тревоги» бизнес
умеет отвечать, в отличие от «какой поставить threshold».

**Общего порога не существует** — у каждого вопроса свой, они могут отличаться в 50 раз.

## Выборка проверяет, что p — это p

Формула работает только при калибровке **в твоём домене**. Вендор обещал калибровку
на своих синтетических данных, про твои тикеты он ничего не обещал.

```js
// bins по 0.1: сколько раз модель сказала ~0.7 — и в скольких реально было true
const bins = Array.from({length: 10}, () => ({n: 0, sumP: 0, hits: 0}));
for (const {p, label} of samples) {
  const b = bins[Math.min(9, Math.floor(p * 10))];
  b.n++; b.sumP += p; b.hits += label ? 1 : 0;
}
const ECE = bins.filter(b => b.n)
  .reduce((s, b) => s + (b.n / samples.length) * Math.abs(b.sumP / b.n - b.hits / b.n), 0);
```

- **ECE < ~0.05** — формула порога применима как есть.
- **ECE большой** — модель не выбрасывать. Ранжирование обычно остаётся нормальным,
  съехала шкала. Лечится одномерной перекалибровкой: **Platt scaling** или
  **isotonic regression**. Два параметра, а не дообучение.

Заодно **Brier score** (`mean((p - label)²)`) — ловит калибровку и дискриминацию одним
числом, удобен как регрессионная метрика.

Прогон 1–2к размеченных примеров стоит центы: $0.042/M input, output бесплатный.

## Порогов должно быть два

```js
if (p > t_hi)      auto_accept();
else if (p < t_lo) auto_reject();
else               human();          // серая зона
```

`t_lo`/`t_hi` — единственное эмпирическое место, и выбираются они не из теории, а из
**пропускной способности людей**: «готовы разбирать руками 8% потока» → бери квантили
распределения `p` так, чтобы в серую зону попадало 8%.

Для `choice` — два независимых сигнала:

```js
const sorted = Object.values(a.queue.probabilities).sort((x,y) => y-x);
const margin = sorted[0] - sorted[1];
if (a.queue.confidence < 0.6 || margin < 0.2) human();
```

Низкий confidence — «не уверена вообще». Низкий margin — «две опции неразличимы».
Бывает confidence 0.8 при margin 0.03, и это повод к человеку.

## Версию пинить

В ответе приходит `jev-1.13.0`, хотя просили `jev-latest` — значит `latest` двигается
под тобой. В проде пинить конкретную версию, размеченную выборку держать как
регрессионный тест (ECE, Brier, доля серой зоны) и прогонять при смене версии.

В проде мониторить распределение `p` и долю серой зоны: поехала доля — поехали входные
данные. Бесплатный детектор дрейфа, он уже лежит в логах.

## Грабли: позиционные индексы

Главный практический результат недели. Измерено на `jev-1.13` 2026-09-18, 320 элементов:

| Как адресуем кандидата | Элементов в запросе | Ошибок | Успех |
|---|---|---|---|
| `candidates[i]` | 150 | 86/320 | **73%** |
| `candidates[i]` | 25 | 29/320 | 91% |
| Объект с ключами `candidates.k137` | 150 | 0/320 | **100%** |
| Элемент вшит внутрь своего вопроса | 320 | 0/320 | **100%** |

Вендорские доки показывают примеры **именно с позиционной индексацией** и про 27%
брака молчат. Правило: ключи или вшивание; массивов с индексами не существует.

## Рабочие паттерны из экосистемы

### Батч-фильтрация без загрузки в контекст
150–300 элементов за запрос, ~250 мс, доли цента. Агент не читает кандидатов — получает
вероятности и работает только с выжившими. Отбор файлов для чтения, ранжирование
результатов поиска, отсев перед дорогим шагом.

### Pre-tool-use gate в shadow-режиме
Гейт перед миграциями, force-push, правками CI, удалением данных. Четыре параллельных
вопроса: уровень риска 0–3, режим одобрения (allow/confirm/block), соответствие задаче,
чувствительный домен. Решение принимает **детерминированная политика поверх чисел**,
не модель.

Ключевое в методологии: **сначала shadow mode**. Гейт логирует рекомендацию и пропускает
действие. Каждая пара «рекомендация + что реально сделал человек» — размеченный пример.
Через неделю есть своя выборка, на ней калибруются пороги.

Измеренная точка отсчёта: `judgeDestructive` — 94.7% на 38 размеченных кейсах,
~$0.0006 за вызов.

### Роутинг скиллов и тулов
Работает, но переоценён. Урок из каталога паттернов: **роутинг по именам ломается** —
«протестируй страницу логина в браузере» уходит в desktop-automation вместо
browser-testing, если слать только имена. Нужны описания.

### Мелочь под наш стек
`jgrep` — семантический греп по коду и диффам через `noul` на чанк. Ранжирование
zsh-истории для инлайн-комплита. macOS computer-use loop с самой цитируемой формулой:
**«Jev выбирает действие за confidence-гейтом, а пишущая модель держится в резерве для
кусков, где нужна проза»**.

## Обязательная инженерия

- **Fail-open.** Недоступность Jev не должна блокировать агента: каждый хук ловит свою
  ошибку и резолвится в `allow`. Иначе аптайм харнесса повешен на alpha-эндпоинт
  недельной давности.
- **Budget guard** — кап запросов в скользящем окне. Агент в цикле сожжёт лимит
  незаметно, потому что отдельный вызов стоит сотую цента.
- **Redaction на клиенте** до отправки: AWS-ключи, JWT, токены. `state` — это состояние
  программы, туда попадает всё.
- **Decision log в JSONL** — без него пороги не перенастроить.
