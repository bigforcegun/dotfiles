# Трек 3. OMO внутри агента и снаружи

## Первый урок: два разных интерфейса

Внутри сессии агент использует OMO tool `task`. Внешний клиент обращается к OpenCode Server/SDK и создаёт или продолжает сессию. Документированного отдельного HTTP endpoint OMO `/task` в рассмотренном Server API нет. Запрос модели «делегируй» не равен прямому API-вызову делегирования. [S3–S8 в [[2026-10-03-omo-learning-sources]]]

```text
Внешний клиент → OpenCode session → основной агент с OMO
                                      ↓ task
                                дочерняя сессия
                                      ↓ результат
                                основной агент → клиент
```

Схема учебная; она не обещает, что каждый prompt обязательно вызовет task.

## Внутреннее делегирование

Выбираем category ИЛИ subagent_type. В коде при передаче обоих category имеет приоритет: это не строгая ошибка взаимного исключения. Практически передавать оба не следует. Пропущенный run_in_background становится false; в примерах указываем явно. [S3, S4]

Иллюстрация вызова инструмента, не shell-команда:

```text
task(
  subagent_type="explore",
  load_skills=[],
  run_in_background=true,
  description="Find authentication entry points",
  prompt="Find authentication entry points. Do not edit. Return paths and evidence."
)
```

Новый делегат получает явное задание и подключённые skills. parentID связывает сессии, но сам по себе не доказывает перенос полного родительского разговора. Существенные ограничения, решения и ожидаемые доказательства передаём явно. [S6]

## Идентификаторы

| Идентификатор | Для чего |
|---|---|
| bg_… | Прочитать результат через background_output; адресовать фоновую отмену |
| ses_… | Продолжить ту же дочернюю сессию через task(task_id=…) |
| Paseo agent ID | Отдельный внешний идентификатор; не подставлять вместо bg_ или ses_ |

После фонового запуска ждём уведомления, затем читаем результат. Продолжение адресуем по ses_ из metadata, не запускаем нового агента без причины. Этот путь уже использован в исследовании курса; это не синтетический тест. [S4, S5, L5; для Paseo S11]

## Внешний клиент

В rolling-документации OpenCode описаны:

1. `POST /session`: создать сессию.
2. `POST /session/:id/message`: отправить сообщение с ожиданием ответа, либо `POST /session/:id/prompt_async` без ожидания.
3. `GET /session/:id/message` и `GET /event`: сообщения и события.
4. `POST /session/:id/abort`: прервать работу сессии.
5. `/doc`: контракт конкретного сервера; сверить его до написания интеграции. [S7]

Сервер и SDK в этом исследовании не запускались. Примеры описывают интерфейс документации, не проверенную совместимость локального build. Если позднее понадобятся smoke-прогоны `opencode run`, локальные правила требуют `OPENCODE_DB=:memory:`.

## Три разных действия остановки

- `background_cancel`: работа фонового менеджера OMO.
- `/stop-continuation`: механизмы автоматического продолжения текущей сессии.
- OpenCode `session.abort`: текущая работа сессии через внешний API.

Нельзя без отдельной проверки обещать, что одно действие каскадно остановит всё, включая дочерние задачи и внешний heartbeat. Практическая рекомендация: при проектировании интеграции назначить владельца каждого жизненного цикла. [S5, S7, S9]

## Упражнение

Фоновая задача вернула bg_123 и ses_456. По какому ID читать результат, а по какому уточнить задание тому же исполнителю? Затем объяснить, почему внешний HTTP-клиент не должен отправлять этот bg_123 в `/session/:id/abort`.
